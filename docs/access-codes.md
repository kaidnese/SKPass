# 卡号是怎么来的：卡型、发行方与 access code

这篇回答一个问题：**我刷一下卡，那串 20 位号码是从哪来的，为什么有时候拿不到？**

对应版本：上位机 v1.0、固件 1.0.0、AimeIO 接口 1.0。数据 HID、UF2 自动重启和 ROM 下载不改变以下卡号解析规则；不确定的地方会明确写成"取决于卡"。

---

## 0. 先分清三个"号"，这是所有困惑的根源

| 名称 | 是什么 | 和卡背印号的关系 |
|---|---|---|
| **UID / IDm** | 卡的物理标识。NFC-A 是 4/7/10 字节 UID，FeliCa 是 8 字节 IDm | **无关**。UID 转成十进制也不是卡号 |
| **CardIO 8 字节标识** | 给兼容 CardIO 的老程序用的 8 字节（HID 报告里那 8 个字节） | **无关**，是历史格式约定 |
| **Access code** | 卡背印的 20 位十进制号码 | 就是它 |

**读到 UID ≠ 读到了卡号。** 上位机把这两件事分开显示，就是为了避免误判。

---

## 1. 先看你的卡是哪一类

| 怎么认 | 类型 | 号码在哪 |
|---|---|---|
| 卡背没有 Amusement IC 标记、通常是哑光塑料卡 | **MIFARE Classic 1K**（含 Classic AiMe，闲鱼兼容卡大多属于这类） | 卡内 Sector 0 的 Block 2（明文 BCD） |
| 卡背有 **Amusement IC** 标记（SEGA/Konami/Bandai Namco/Taito 联名） | **FeliCa（Lite / LiteS）** | 卡内 **S_PAD0**（加密，需本地解密） |
| 老式 Banapass 等 | FeliCa，但卡内格式不一 | 没有通用算法，取决于卡内数据 |
| 其它 NFC-A/B、ISO15693 | — | 拿不到印号，只能读标识 |

上位机「读卡概览」会显示卡类型、UID/IDm、号码和**来源**，可以拿来对照。

## 2. Classic 卡（MIFARE Classic 1K）：号码直接读出来

### 步骤（固件做的事）

1. 确认这是一张 Classic 卡：`mode=00`，且 `protocol=0x80` 或 SAK ∈ {`0x08`,`0x18`,`0x09`}。
   SAK 不是这几个、或不是 MIFARE Tag-command 接口（`interface != 0x80`）时，直接返回状态 `0x15`，不尝试读取。
2. **先免认证试读** Sector 0 的 Block 0、1、2。有些克隆卡允许免认证读数据块。
3. 免认证失败 → **认证再读**：
   * 认证命令：`40 00 10 <6 字节 Key>`（走 PN7150 的 MIFARE Tag-command，**不是**直接发 RF 的 `60/61`）；
   * Key A 来自 Kconfig `SKPASS_MIFARE_KEY_A`，默认 `574343467632`（ASCII `WCCFv2`）；
   * 若认证返回失败，会再用一次空白卡出厂密钥 `FFFFFFFFFFFF`；两者相同时不重复尝试。
4. 读块命令：`10 30 <block>`。必须收到 `n==18 且 rx[0]==0x10 且 rx[17]==0` 才算成功。
5. 容错：每次 READ / 重选 / 认证前有帧间隔（100 Hz 节拍下实际约 20 ms）；每种 Key 最多 3 次认证尝试；每块最多 3 次尝试，补试会**重新 Sleep→Select 再重新认证**；超过就放弃并清空 48 字节。
6. 只有三块**全部**成功，才会把 48 字节发给上位机；否则状态码是 `0x12`（认证失败）或 `0x13`（读块/重选/会话失败），且 `mifare_len=0`。

### 号码在 48 字节里的位置

上位机优先取**偏移 38 起的 10 字节**（= Block 2 起始 32 + 块内偏移 6）：

```text
Sector 0（48 字节）
Block 0: UID + 厂家信息（16 字节）
Block 1: 通常全 0（16 字节）
Block 2: 00 00 00 00 00 00 C0 C1 C2 C3 C4 C5 C6 C7 C8 C9
                            └────── 20 位号码（BCD）──────┘
                            偏移 38 ↑
```

BCD 的规则：每个字节高半字节和低半字节都必须是 `0–9`，两个半字节直接拼成两位十进制数字，10 字节 → 20 位。全 0 视为"没有号码"。

如果固定位置解不出来，上位机会在整段数据里**滑动扫描**，但只采用满足下面全部条件的候选：

* BCD 结构合法且不为全 0；
* 以已知号码前缀开头：`01036`、`3`、`500`、`501`、`510`、`520`、`530`；
* **扫描结果必须恰好只有一个候选**，否则拒绝（显示"多个BCD候选，无法确定卡号"）。

> AimeIO DLL 不做这个扫描，它只认固定偏移 38。所以极端情况下上位机可能显示号码而游戏拿不到，这是有意的保守设计。

### 读失败代表什么

| 状态 | 含义 | 不是 |
|---|---|---|
| `0x12` | 认证没通过：Key A 不对、访问控制不允许、或 RF 会话失败 | **不是"这张卡是空白卡"** |
| `0x13` | 读块/重选/会话失败（已重试过） | 不是"卡里没有号码" |
| `0x15` | 不是 MIFARE Tag-command 接口 | — |

即使读块失败，UID 仍然是显示出来的 —— 那只是卡的身份，不是号码。

## 3. FeliCa / Amusement IC：号码在 S_PAD0 里，需要解密

### 步骤（固件做的事）

1. 确认 FeliCa：`mode=02` 且 IDm 长度 8；PMm 无效时状态 `0x14`。
2. 用 **Read Without Encryption（命令 `0x06`）** 只读块，帧格式：
   `10 06 <IDm:8> 01 <服务码:2> 01 80 <块号>`
3. 探测顺序：先读 **ID 块 `0x82`**（拿发行方 DFC），再读 **S_PAD0 块 `0x00`**（拿卡号密文）。
   服务码会依次尝试 4 种线上写法：`0B 00`、`00 0B`、`09 00`、`00 09`。
4. 打开 `SKPASS_FELICA_FULL_SCAN`（默认开）时，还会对块 `0x00–0x0D` 与 `0x80–0x88` 全量只读扫描，把每次的服务码/块号/`status1`/`status2` 写进日志（跳过 `0x0E–0x7F`、`0x00`、`0x82`，因为它们已在前面读过）。
5. 只接受**内容有效**的响应：`rx[1]==0x07`、`rx[2..9]` 等于 IDm、`status1==0`、`status2==0`、`rx[12]==1`、长度匹配。任何一条不满足就丢弃。

**固件不解析 S_PAD0**，它只把 16 字节原样送给上位机 —— 解密是电脑端的事。

### 上位机怎么解（本地，无需密钥）

```
密文 16 字节
  ↓ 用第 9 张置换表求逆，逐字节反掩码
参数：轮数 count = (d[15] >> 4) + 7；起始表号 table = d[15] + 5*count
  ↓ 循环 count 次：
     table -= 5
     对前 15 字节整体右移 5 位（含字节间借位，第 15 字节补位）
     用 inv[table % 8] 逐字节替换前 15 字节
校验：明文 [0] & 0x0F 必须为 0（版本低半字节）
取号：明文偏移 6..15 的 10 字节 BCD → 20 位号码（全 0 视为无效）
```

* 表共 **9×256 = 2304** 字节，逐字节取自公开实现 micetools 的 `SPAD0_SPN_TABLE`，见 [第三方声明](../THIRD_PARTY_NOTICES.md)。
* **没有任何密钥**：所有参数都藏在密文第 16 字节里，谁拿到这 16 字节都能离线解开。所以瓶颈不在解密，而在**能不能读到那 16 字节**。

### 读不到 S_PAD0 的原因（状态 `0x11`）

FeliCa Lite-S 允许把 S_PAD 区配置成"必须认证后才能读"。此时：

* 所有服务码写法都会返回错误，典型是 `status2 = 0xA7`（块访问不允许）或 `0xA6`（非法服务码）；
* 日志里能看到逐条探测结果，据此可以区分"卡不允许"和"服务码写法不对"；
* 这种情况**没有退路**：没有服务端映射表就恢复不出印号，只能用下面的替代方案。

顺带：ID 块 `0x82` 的**字节 8~9 是 DFC**，用来判断发行方（见第 5 节）。

## 4. 上位机显示时的"来源"字段很重要

| 界面显示的来源 | 含义 | 你要做什么 |
|---|---|---|
| 来自卡内数据（未核对印号） | Classic Block 2 的 BCD | **和卡背对一次** |
| 来自 S_PAD0 | 本地解密出来的 | 和卡背对一次 |
| 来自写卡回读（非官方注册证明） | 刚写进去的号码，回读一致 | 只是证明写成功了 |
| **派生号（非卡背印号）** | IDm 换算出来的，**不是印号** | 别拿去和卡背比，它只是给"按 IDm 认卡"的服务器用 |
| 手动输入 / Serial 计算 / 随机生成 | 你自己给的 | 各自看下面第 6 节 |

派生号的算法：把 8 字节 IDm 当**大端有符号 64 位整数**取绝对值，十进制后左补 `0` 到 20 位；IDm 全 0 时不生成。它恒以 `0` 开头（真实印号通常以 `5xx` 开头，一眼能区分）。

## 5. 发行方是怎么判断的

两类证据，**都不是认证**，只是提示：

**证据一：FeliCa ID 块 `0x82` 的 DFC（字节 8~9）**

| DFC | 发行方 |
|---|---|
| `0078` | SEGA（Lite-S） |
| `0068` | Konami（Lite-S） |
| `002A` | Bandai Namco Entertainment（Lite-S） |
| `003A` | Bandai Namco Games（Lite） |
| `0079` | Taito / NESiCA |
| `8CA2` | 旧 Banapass（Edy） |
| `0000` | 测试保留，发行方不确定 |

**证据二：号码前缀**

| 前缀 | 发行方 |
|---|---|
| `01036`、`500`、`501` | SEGA |
| `3`、`510` | Bandai Namco |
| `520` | Konami |
| `530` | Taito |

两类证据冲突时，上位机会提示"DFC与卡号前缀不一致，请核对"；DFC 没读到就显示未知 —— **不会拿 UID 去猜发行方**。

## 6. 拿不到印号时的替代做法

### 6.1 手动输入（最可靠）

直接输入或粘贴 20 位卡背号。输入会自动规整：忽略空格、`-`、`–`、`—`，全角数字 `０–９` 转半角。校验只有三条：

1. 必须正好 20 位 ASCII 数字；
2. 不能全 0；
3. 以 `01036` 开头时额外做一次摘要校验（见下）。

其它前缀只做格式检查 —— **格式合法不代表这张卡真实存在或在服务器注册过**。

### 6.2 用 8 位 Serial 计算（只对 `01036` 体系）

```
Access Code = "01036" + 牌堆加密(明文 Serial, 8 位) + 摘要(7 位)
```

* 摘要：`MD5(Serial 左补 0 到 8 位)` → 按密钥 `A1B3E86CF02974D6` 的每个字符取 MD5 中对应字节 → 组成 128 位 → 整体位序反转 → 左补 0 到 138 位 → 按 23 位分 6 组异或 → 7 位十进制。
* 加密：22 张牌（含 2 张 Joker）的 solitaire 变体，密钥就是那 7 位摘要。
* 反查：由 `01036…` 卡号反推出 Serial，并用摘要校验，失败会报"卡号摘要校验失败"。

**这里的 Serial 是 8 位十进制明文序号，不是 UID。** 把 UID 转成十进制填进去只会得到错误号码。

### 6.3 随机生成（只给自己制卡用）

随机取 0–99999999 作为 Serial，再按上式生成 `01036…` 号码。它只填进输入框，**不会自动保存或写卡**；不保证唯一，也不代表官方发卡。

## 7. 为什么游戏显示的号码和上位机不一样

AimeIO DLL 的呈卡规则（代码实际行为）：

| 情况 | 上位机显示 | AimeIO 给游戏 |
|---|---|---|
| Classic 完整读取且固定偏移有效 | 卡内 BCD 号码 | 10 字节号码，走 **AiMe ID** 接口 |
| FeliCa S_PAD0 解密成功且格式有效 | 本地解出的号码 | **同一个号码**，也走 AiMe ID 接口 |
| FeliCa 没解出有效号码 | 派生号（明确标注非印号） | **原始 IDm**（走 FeliCa ID 接口），DLL 不做任何换算 |
| Classic 读取失败 | UID + 失败原因 | 不呈现，绝不伪造号码 |
| 虚拟卡（按键呈卡） | JSON 里保存的号码 | 直接呈现该号码；实体卡优先 |

其它会影响观感的点：

* DLL 认为**卡的有效期是 5 秒**（5 秒无新数据就当没卡）；
* 实体卡优先于虚拟卡；
* 虚拟卡只支持 Classic 那种 20 位号码形式，不保存虚拟 FeliCa 身份。

所以**看到 20 位数字不等于成功**：要同时看号码、来源、以及原始数据是否完整。

## 8. 联网查卡号？没有

**固件、上位机、AimeIO DLL 全都不联网**，没有 `aqua.naominet.live`、没有 TCP 22345、没有 AiMeDB 查询，也没有账号注册。

之前讨论过的服务端方案（packet header、社区服接口）**只是方案**，没有进入任何一行已发行代码。号码全部来自：卡内数据、S_PAD0 本地解密、或你的手工输入。

游戏自己的网络登录由游戏/segatools 完成，与本读卡 DLL 无关；呈卡成功也不代表服务器已有账号。
